# Malanta — סליקה כקופסה סגורה

**הדרישה כפי שנוסחה:** משתמש מגיע לעמוד סליקה חיצוני, מזין פרטי אשראי ושם,
ואני מקבל אישור תשלום עם שם ומייל — ומשייך למשתמש באתר בהצלבה.

המסמך הזה מקבל את הדרישה כמו שהיא: **Malanta לא נוגעת בכרטיס אשראי, לא מחזיקה
טוקן, ולא יודעת מי הספק.** מה שהוא כן עושה — הופך את ה"הצלבה" מהנחה
לתהליך שיודע להיכשל בבטחה.

---

## 1. למה הצלבת שם+מייל לבדה לא מספיקה

זה לא עניין של אבטחה בלבד. אלה שישה מצבים שיקרו בוודאות, לא במקרה קיצון:

| מצב | תוצאה עם הצלבת מייל בלבד |
|---|---|
| שילם עם `yosi@gmail.com`, נרשם עם `yossi@gmail.com` | שילם, אין גישה, ואין לך דרך לדעת |
| שילם עם המייל של בן/בת הזוג | תשלום יתום |
| שילם, ונרשם רק בעוד יומיים | חייב תהליך "התאמה מאוחרת", אחרת אבוד |
| קנה שתי מפות מאותו יוצר | שני תשלומים, אותו מייל — **לאיזו מפה?** |
| חידוש מנוי | תשלום זהה למייל שכבר יש לו גישה — הארכה או חדש? |
| **זיכוי / chargeback** | אין שום דרך לדעת איזו גישה לבטל |

השורה הרביעית והשישית הן החמורות: **מייל אינו מזהה את הרכישה, רק את הקונה.**
בלי מזהה לרכישה עצמה, אתה לא יכול לדעת מה נקנה, ולא יכול לבטל.

**מבחינה אבטחתית:** אם מייל הוא המפתח, אז מי ששולט במייל שולט ברכישה.
זה מתקבל — אבל רק בתנאי אחד קשיח: **שיוך אוטומטי מתבצע רק מול מייל מאומת.**
בלי אימות מייל, כל אחד שיודע שאדם מסוים קנה יכול להירשם עם המייל שלו ולקבל את הגישה.

## 2. הפתרון: token של כוונת רכישה

**שאלה אחת לספק הסליקה, לפני הכל:**

> האם ניתן להעביר פרמטר חופשי משלי לעמוד התשלום, ולקבל אותו חזרה
> בקריאת ה-callback/IPN שרת-לשרת?

כמעט כל ספק ישראלי (Tranzila, Cardcom, PayPlus, Meshulam/Grow, iCount, Green Invoice)
תומך בזה — בשמות שונים: `custom`, `more_info`, `ReturnValue`, `udf1`, `Order`.
**אם התשובה כן — כל המסמך הזה עובד. אם לא — להחליף ספק.** זו סיבה מספקת.

הרעיון: לפני שהמשתמש נשלח לסליקה, נוצרת שורת `purchase_intents`.
ה-`id` שלה (uuid) נוסע איתו לדף התשלום, וחוזר עם אישור התשלום.
עכשיו לתשלום יש **מזהה של הרכישה**, לא רק של הקונה.

המייל לא נזרק — הוא הופך ל**גיבוי**, וזה בדיוק התפקיד הנכון שלו.

## 3. הזרימה המלאה

```
  ┌─ שלב א׳: כוונה ─────────────────────────────────────────────┐
  │  משתמש לוחץ "קנה גישה"                                       │
  │  → createPurchaseIntent({ kind, map_id, offer, amount })     │
  │  → שורה ב-purchase_intents, status='pending', תוקף שעתיים    │
  │  → redirect לעמוד הספק עם ?custom=<intent_id>                │
  └──────────────────────────────────────────────────────────────┘
                              ↓
  ┌─ שלב ב׳: תשלום (קופסה סגורה) ───────────────────────────────┐
  │  עמוד הספק. פרטי אשראי + שם + מייל.                          │
  │  Malanta לא רואה, לא שומרת, לא מלגגת. אפס היקף PCI.          │
  └──────────────────────────────────────────────────────────────┘
                              ↓
        ┌───────────────────┴────────────────────┐
        ↓                                        ↓
  ┌─ redirect ────────────┐        ┌─ callback שרת-לשרת ────────────┐
  │  המשתמש חוזר לאתר.    │        │  ⚠️ *זה* מקור האמת.            │
  │  מסך "מעבדים…".       │        │  1. אימות חתימה                │
  │  ⚠️ לא מעניק כלום.    │        │  2. payment_events (idempotent)│
  │  UI בלבד.             │        │  3. אימות סכום+מטבע מול intent │
  └───────────────────────┘        │  4. שורת payments              │
                                   │  5. שיוך                       │
                                   │  6. grantAccess                │
                                   └────────────────────────────────┘
```

**החוק הכי חשוב בכל הזרימה: ה-redirect לא מעניק גישה.**
משתמש שעורך את ה-URL בחזרה, או פשוט מרענן, לא מקבל כלום.
רק ה-callback שרת-לשרת, עם חתימה מאומתת, מעניק.

## 4. סולם השיוך — שלוש דרגות, לפי סדר

```
1. intent_token   — ה-token חזר מהספק ותקף
                    → 100% ודאות. מה נקנה ומי קנה, שניהם ידועים.

2. email_verified — אין token, אבל payer_email תואם profile עם מייל מאומת
                    → נדרש גם: intent פתוח תואם, או מוצר יחיד חד-משמעי

3. manual         — לא זוהה. נכנס לתור הטיפול הידני.
                    → אף פעם לא "ניחוש הכי קרוב". אף פעם לא לפי שם בלבד.
```

**דרגה 3 היא לא כישלון — היא הפיצ׳ר.** במקום 2% מהתשלומים שנעלמים בשקט,
יש רשימה שאתה עובר עליה פעם ביום, ולוחץ "שייך ל…". בקנה מידה של
5–50 יוצרים זה שתי דקות בשבוע, וזה **הרבה יותר טוב** משיוך אוטומטי ששוגה.

### "שילמתי ואין לי גישה" — התהליך שסוגר את הפער

```
תשלום מגיע → אין token → אין profile מאומת עם המייל הזה
  → payments.matched_user_id = null
  → מייל למשלם:  "התשלום התקבל. להשלמת הגישה — הירשם עם <email>."   ← קישור
  → המשתמש נרשם, מאמת מייל
  → טריגר בהרשמה: יש payment לא משויך עם email_norm תואם?
      כן → שיוך (match_method='email_verified') → grantAccess → מייל אישור
```

**זו בדיוק ה"הצלבה" שתיארת — רק עם שני שינויים שהופכים אותה לבטוחה:**
1. היא מתבצעת **רק אחרי אימות מייל**
2. היא **דרגה 2**, לא דרגה 1 — רוב התשלומים לא יגיעו לכאן בכלל

## 5. קוד — השירות שסוגר את המעגל

```ts
// lib/services/payments/reconcile.ts
import 'server-only';

export async function handleProviderCallback(req: Request) {
  const raw = await req.text();

  // 1 ─ חתימה לפני הכל. גוף לא מאומת אף פעם לא מגיע ללוגיקה עסקית.
  if (!verifySignature(raw, req.headers)) {
    await recordEvent({ raw, verified: false });
    return new Response('ok', { status: 200 });   // ⚠️ 200, לא 401
  }

  const evt = parseProviderPayload(raw);

  // 2 ─ Idempotency. ספקים שולחים כפילויות; רשת נכשלת; אנשים מריצים retry.
  //     unique(provider, provider_event_id) הוא מה שמונע הענקה כפולה.
  const { inserted, event } = await insertPaymentEvent(evt);
  if (!inserted) return ok();   // כבר טופל

  // 3 ─ הסכום נבדק בצד שרת מול ה-intent. לעולם לא סומכים על מה שהגיע.
  const intent = evt.customParam ? await getIntent(evt.customParam) : null;
  if (intent && (intent.amount_minor !== evt.amountMinor
              || intent.currency    !== evt.currency)) {
    await flagForReview(event, 'amount_mismatch');
    return ok();
  }

  // 4 ─ עובדה כספית
  const payment = await upsertPayment({
    provider: evt.provider,
    providerPaymentId: evt.paymentId,
    intentId: intent?.id ?? null,
    payerName: evt.payerName,
    payerEmailNorm: normalizeEmail(evt.payerEmail),
    amountMinor: evt.amountMinor,
    currency: evt.currency,
    status: evt.status,          // captured | refunded | chargeback | failed
    rawEventId: event.id,
  });

  // 5 ─ זיכוי/chargeback הולכים למסלול הפוך
  if (payment.status === 'refunded' || payment.status === 'chargeback') {
    await revokeAccessForPayment(payment.id, payment.status);
    return ok();
  }

  // 6 ─ סולם השיוך
  const match = await resolveBuyer(payment, intent);
  if (!match) {
    await queueForManualMatch(payment);
    await sendClaimEmail(payment);      // "הירשם עם <email> להשלמת הגישה"
    return ok();
  }

  // 7 ─ הענקה. מקום אחד בלבד במערכת שכותב ל-map_access (כלל 5).
  await grantAccess({
    userId:    match.userId,
    mapId:     intent!.map_id,
    scope:     null,
    expiresAt: computeExpiry(intent!.offer_code),
    source:    'payment',
    sourceRef: payment.id,
  });

  await markIntentFulfilled(intent!.id);
  await sendAccessEmail(match.userId, intent!.map_id);
  return ok();
}
```

### חמש נקודות שקל לפספס בקוד הזה

1. **`200` על חתימה שגויה.** החזרת `401` אומרת לתוקף "החתימה נבדקת ונכשלה".
   `200` + רישום שקט + התראה פנימית. אותו היגיון כמו `not_found` במקום `forbidden`.
2. **הרישום ל-`payment_events` קודם לכל עיבוד.** אם הלוגיקה קורסת, הכסף מתועד.
   `processed_at is null` הוא תור השחזור.
3. **`grantAccess` היא הפונקציה היחידה במערכת שכותבת ל-`map_access`.** אם יש שנייה,
   הזיכויים יפספסו אותה ותהיה גישה בתשלום שבוטל.
4. **`revokeAccessForPayment`** — הצד השני של אותו מטבע. בלעדיו chargeback משאיר
   גישה פעילה: הלקוח קיבל את הכסף בחזרה ואת המוצר.
5. **הכל עובר ל-`audit_log`.** "למה ללקוח הזה יש גישה" חייבת להיות שאלה עם תשובה.

## 6. שני זרמי כסף שונים — הבחנה שחייבת להיות מפורשת

התכנון מזכיר שני ערוצי רכישה. בסליקה הם **שני עולמות שונים לגמרי**:

### א׳. מנוי יוצר לפלטפורמה (99–149 ₪/חודש) — הכסף שלך

- **אתה** סוחר-הרשומה (merchant of record)
- חייב חשבונית/קבלה — לחבר Green Invoice / iCount / Morning לספק הסליקה
- מנוי מתחדש → צריך לטפל בכשל חיוב, ובהתראה לפני ניתוק
- `kind = 'platform_subscription'`, ה-intent קשור ל-`tenant_id`

### ב׳. מטייל קונה מיוצר (Creator-led) — הכסף **לא** שלך

- **היוצר** סוחר-הרשומה. הוא מנפיק את החשבונית, הוא סופג את הזיכוי
- Malanta רק **מספקת גישה** — `source='manual'` או `'payment'` לפי הסידור
- **זו העמדה הנכונה מבחינה משפטית ורגולטורית ל-MVP.** אל תיגע בכסף של אחרים

### ג׳. Marketplace — לא לבנות, אבל לדעת מה מחכה

ברגע ש-Malanta גובה ומעבירה ליוצרים, אתה בעולם אחר:
תשלומים מפוצלים / sub-merchants, אחריות על זיכויים של מוכר אחר, KYC על היוצרים,
דיווח הכנסות. בישראל זה דורש ספק שתומך במפורש בסאב-סוחרים (Tranzila/PayPlus).
**החלטה גדולה. לא ב-MVP. אבל הסכמה כאן כבר תומכת בה** —
`purchase_intents.tenant_id` קיים בדיוק לשם כך.

## 7. היקף PCI — ההחלטה שקובעת כמה "סגורה" הקופסה

| מבנה | היקף | המלצה |
|---|---|---|
| Redirect לדומיין של הספק | SAQ A — מינימלי | ✅ |
| iframe **מהדומיין של הספק** | SAQ A | ✅ |
| טופס בדומיין שלך שמדבר עם ה-API של הספק | SAQ A-EP — רחב משמעותית | ❌ |
| שרת שלך נוגע במספר הכרטיס | SAQ D | ❌❌ |

הניסוח "משתמש יגיע לעמוד הסליקה" מתאים לשתי השורות העליונות.
**רק לוודא מפורשות שהעמוד הוא של הספק ולא עמוד שלך שנראה כמו שלו.**

בכל מקרה, ובלי קשר להיקף:
- לעולם לא ללגלג payload של סליקה — לא ב-Sentry, לא בקונסולה, לא ב-`payment_events`
  אם הספק מחזיר PAN חלקי מעבר ל-4 ספרות אחרונות
- להוסיף redaction ב-Sentry לשדות `card`, `cvv`, `pan`, `token`
- מפתחות הספק ב-Vercel **Production בלבד**, לא Preview

## 8. מה לבנות עכשיו, מה לדחות

ה-MVP חתך חיוב — **צודק**. אבל שתי מיגרציות עכשיו חוסכות שכתוב אחר כך:

**עכשיו (במיגרציה הראשונה, עלות ~0):**
- ✅ שלוש הטבלאות: `payment_events`, `purchase_intents`, `payments`
- ✅ `map_access.source` + `source_ref` + `revoked_at` + `revoke_reason`
- ✅ `grantAccess(userId, mapId, scope, expiresAt, source, sourceRef)` — החתימה המלאה
- ✅ `revokeAccess(mapAccessId, reason)` — הצד ההפוך, מהיום
- ✅ `profiles.email_norm` — עמודה מחושבת + unique

**בשלב 7 (הענקת גישה ידנית):**
- `grantAccess` עם `source='manual'` מפאנל היוצר. אותה פונקציה בדיוק.
- אם היא נכתבה נכון — חיבור הסליקה בעתיד הוא **route handler אחד**, לא שכתוב.

**אחר כך:**
- ה-callback עצמו, אימות החתימה, תור השיוך הידני
- מנויים מתחדשים, חשבוניות
- Marketplace

**הבדיקה שהתכנון הזה נכון:** אם `grantAccess` נכתבת עם החתימה המלאה בשלב 7,
אז ביום שתחבר סליקה לא תיגע באף שורה קיימת. זה כל המבחן.
